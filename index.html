Introduzione al Blue Team

Il Blue Team difende, investiga e ricostruisce. In una CTF significa analizzare artefatti, trovare flag nascoste nei log, nei dump, nei PCAP, nelle immagini disco.

Framework di riferimento

NIST SP 800-61

È lo standard internazionale per la gestione degli incidenti. Definisce un ciclo in 4 fasi che tutte le organizzazioni mature seguono. Sapere dove sei nel ciclo ti orienta.
4 fasi: Preparation (preparazione), Detection & Analysis (rilevamento e analisi), Containment/Eradication/Recovery (contenimento, eradicazione, ripristino), Post-Incident Activity (attività post-incidente).
In CTF usi solo la fase 2 (Detection & Analysis) perché non c'è un host reale da contenere. Ma conoscerle tutte ti serve per capire il contesto professionale.

MITRE ATT&CK

È il catalogo di riferimento delle tecniche di attacco osservate in incidenti reali. Ti dice cosa cercare quando analizzi un artefatto.
Organizzato in tattiche (obiettivi: Initial Access, Execution, Persistence...) e tecniche (T1059 PowerShell, T1003 Credential Dumping). Ogni tecnica ha un codice univoco.
Usalo per nominare ciò che trovi nel report e per capire quali tecniche cercare nei log. Es. se sospetti Kerberoasting, cerchi T1558.003.

Pyramid of Pain

Gerarchizza gli indicatori in base a quanto costano all'attaccante quando vengono bloccati. Più sali, più è difficile per l'attaccante cambiare.
Dal basso: hash < IP < dominio < artefatti di rete/host < tool < TTP. Bloccare un hash costa zero all'attaccante; caratterizzare una TTP lo obbliga a ripensare il modus operandi.
In CTF cerca TTP e artefatti, non solo hash. Un report che si ferma agli IoC è fragile; un report che arriva alle TTP è resistente.

Diamond Model

Struttura l'analisi di un'intrusione su 4 vertici correlati. Ti aiuta a non fermarti alla prima informazione.
4 vertici: Adversary (chi), Capability (cosa usa), Infrastructure (da dove), Victim (chi subisce). Se conosci 3 vertici, puoi inferire il 4°.
Utile per strutturare il report finale. Se un vertice resta vuoto, l'investigazione non è completa.

Ordine di volatilità (RFC 3227)

Regola d'oro dell'informatica forense: acquisisci prima le cose che si perdono prima. Se sbagli l'ordine, perdi evidenza irreversibile.
Registri CPU e cache (si perdono in millisecondi) → RAM (allo spegnimento) → stato rete (connessioni attive) → processi attivi → file system e file cancellati → log remoti → configurazione sistema → archivi.
Sempre, in ogni acquisizione. In CTF non acquisisci (i dati sono già lì), ma l'ordine ti dice cosa analizzare prima: RAM prima del disco, rete prima dei log.

Ordine operativo in CTF

In CTF hai tempo limitato e un pacchetto di artefatti già pronti. Un ordine chiaro ti fa risparmiare minuti preziosi.
  1. Leggi la traccia: cosa ti danno? (PCAP, dump, log, disk image). Cosa devi trovare? (flag, IP, utente, timestamp).
  2. Identifica la fonte primaria e inizia da lì. Se hai PCAP + dump, inizia dal PCAP (più navigabile).
  3. Overview prima dei dettagli: Statistics in Wireshark, windows.info in Volatility, mmls in TSK.
  4. Documenta ogni comando e output.
  5. Correla fonti diverse per ricostruire la timeline.
Sempre, all'inizio di ogni challenge. Non improvvisare.

3.1 Network Forensics

Il PCAP è la fonte di verità: registra tutto ciò che è transitato in rete. Se c'è un PCAP, inizia da lì.

Perché il PCAP è la fonte più affidabile

Un attaccante può cancellare i log del sistema, ma se il traffico è stato catturato su un sensore fuori dal suo controllo (TAP di rete, SPAN port del firewall, sensore IDS), quella copia è intoccabile. In CTF il PCAP è quasi sempre la fonte primaria.
Il PCAP è un archivio cronologico completo di tutti i pacchetti transitati. Ogni pacchetto è stratificato L2/L3/L4/L7. Wireshark lo decodifica automaticamente.
Quando hai un file .pcap o .pcapng. Sempre come primo passo in una CTF di network forensics.

Anatomia di un pacchetto

Ogni pacchetto è stratificato come una cipolla. Sapere cosa c'è in ogni strato ti dice cosa cercare e dove.
  • L2 Ethernet: MAC sorgente/destinazione, EtherType
  • L3 IP: IP sorgente/destinazione, TTL, Protocol (TCP=6, UDP=17, ICMP=1)
  • L4 TCP/UDP: porte, flag (SYN, ACK, FIN, RST), sequence number
  • L7 Application: HTTP, DNS, TLS, SMB, Kerberos, LDAP
Ogni volta che analizzi un pacchetto. Il TTL ti dice quanti hop ha fatto il pacchetto (TTL 64 = locale, 128 = Windows, 255 = router). Le porte ti dicono il servizio (22=SSH, 80=HTTP, 443=HTTPS, 445=SMB, 3389=RDP, 53=DNS).

Wireshark - Primo approccio

Non aprire un PCAP e iniziare a scorrere pacchetti: perdi ore. Fai sempre l'overview prima. 5 minuti di overview fanno risparmiare 30 minuti di analisi sbagliata.
  1. Statistics > Capture File Properties: durata, numero pacchetti, volume. Ti dice se il PCAP è piccolo (analizzabile a mano) o grande (serve filtrare).
  2. Statistics > Protocol Hierarchy: gerarchia protocolli. Se vedi 90% TLS, sai che lavorerai sui metadata TLS. Se vedi DNS anomalo, parti da lì.
  3. Statistics > Conversations: coppie IP/porta con volume. Le conversazioni più voluminose sono quelle da investigare per prime.
  4. Statistics > Endpoints: host più attivi. Un host che parla con 50 IP diversi è sospetto (scan o C2).
Sempre come primo passo dopo l'apertura di un PCAP. Non saltare.

Filtri display essenziali

I filtri display non modificano il PCAP: filtrano solo la vista. Puoi applicarli e rimuoverli senza perdere dati. Sono lo strumento principale di lavoro.
# Filtra per IP specifico
ip.addr == 10.0.0.5

# Filtra per IP sorgente E porta
ip.src == 192.168.1.10 && tcp.port == 443

# Solo traffico HTTP (non HTTPS)
http

# Solo richieste POST (login, upload)
http.request.method == "POST"

# Solo DNS
dns

# Query DNS contenenti stringa sospetta
dns.qry.name contains "evil"

# Solo handshake TLS (ClientHello)
tls.handshake.type == 1

# Solo pacchetti SYN (nuove connessioni)
tcp.flags.syn == 1 && tcp.flags.ack == 0

# Solo reset TCP (connessioni rifiutate)
tcp.flags.reset == 1

# Kerberos AS-REQ (richiesta TGT)
kerberos.msg_type == 10

# Kerberos TGS-REQ (richiesta ticket servizio)
kerberos.msg_type == 12

# Solo SMB2
smb2

# Solo autenticazione NTLM
ntlmssp
Quando vuoi restringere la vista su un sottoinsieme di pacchetti. Scrivi il filtro nella barra in alto di Wireshark e premi Enter.

HTTP - cosa cercare

HTTP non cifrato è una miniera: credenziali, sessioni, file scaricati, comandi C2. Anche HTTPS ha metadata utili.
  • User-Agent inusuale (curl, python-requests su traffico utente). Un browser normale ha User-Agent lungo; un malware ha User-Agent corto o assente.
  • Authorization: Basic - credenziali in Base64 decodificabili.
  • POST con payload binari o base64 grandi. Login, upload, C2 beacon.
  • Cookie di sessione. Se rubati, session hijacking.
  • Referer per percorso navigazione.
# Decodifica Basic Auth: prendi la stringa dopo "Basic " e decodificala
echo "dXR1bnR10nBhc3N3b3Jk" | base64 -d
# Output: utente:password

# Export oggetti HTTP: File -> Export Objects -> HTTP
# Salva tutti i file trasferiti (HTML, immagini, eseguibili, PDF)
# Poi analizza i file separatamente (es. exe scaricato = malware)
Quando vedi traffico HTTP non cifrato nel Protocol Hierarchy. Cerca sempre credenziali (Basic Auth) e file scaricati (Export Objects).

DNS - la porta d'ingresso

Il DNS precede quasi ogni comunicazione: prima di connettersi a un dominio, il client chiede l'IP. Quindi il DNS rivela tutto: quali domini sono stati contattati, quando, da chi.
  • Query verso domini sospetti (nomi casuali, TLD strani)
  • Volume anomalo verso singolo dominio (DNS tunneling: dati esfiltrati nelle query)
  • Sottodomini ad alta entropia (DGA: malware genera domini casuali)
  • Query TXT verso destinazioni inusuali
  • NXDOMAIN massivi (DGA che prova domini non registrati)
# Query DNS contenenti "malware"
dns.qry.name contains "malware"

# Solo query TXT (record 16)
dns.qry.type == 16

# Solo NXDOMAIN (rcode 3 = dominio inesistente)
dns.flags.rcode == 3
Sempre dopo l'overview. Il DNS è la prima cosa da analizzare perché rivela la mappa delle comunicazioni.

TLS - metadata non cifrati

TLS cifra il contenuto, ma l'handshake è in chiaro. Da lì estrai il dominio (SNI), il certificato, la cipher suite. Anche senza chiavi, sai chi ha parlato con chi.
  • SNI (Server Name Indication): dominio richiesto in chiaro.
  • Certificato server: CN, SAN, CA, date. Un certificato self-signed su un sito che dovrebbe averne uno di CA è sospetto.
  • Cipher suite negoziata. Suite deboli (RC4, 3DES) = configurazione vecchia.
  • JA3/JA4: fingerprint client TLS. Ogni client ha un fingerprint diverso. Utile per identificare malware noto.
tls.handshake.extensions_server_name
tls.handshake.type == 1
Quando il traffico è prevalentemente TLS (HTTPS). Anche se non decifri, i metadata ti dicono cosa cercare.

Kerberos - attacchi rilevabili

In reti Active Directory, Kerberos è il protocollo di autenticazione. Attacchi come Kerberoasting lasciano tracce visibili nel traffico.
  • AS-REP Roasting: AS-REP con pre-auth disabilitata. L'attaccante chiede un AS-REP per un utente senza pre-auth e riceve materiale cifrato con la password.
  • Kerberoasting: TGS-REQ per SPN, risposta cifrata con RC4 (0x17). In ambienti AES-only, RC4 è IoC quasi perfetto.
  • Golden/Silver Ticket: ticket forgiati. Encryption type anomalo (RC4 in ambiente AES) è il segnale.
kerberos.msg_type == 10  # AS-REQ
kerberos.msg_type == 12  # TGS-REQ
kerberos.CNameString contains "admin"
Quando il PCAP è di una rete Active Directory. Cerca AS-REQ/TGS-REQ anomali e encryption type RC4.

Pattern C2 (Command and Control)

Il malware parla con il server dell'attaccante. Il pattern è spesso regolare (beaconing) o nascosto dietro servizi legittimi (domain fronting).
  • Beaconing: connessioni regolari a intervalli costanti. Es. ogni 60 secondi, ogni 5 minuti. Calcola la deviazione standard degli intervalli: se è bassa, è sospetto.
  • Domain fronting: C2 dietro CDN legittimo (CloudFlare, AWS). Il traffico TLS sembra verso un sito popolare, ma il vero destinatario è nell'header Host HTTP cifrato.
  • DGA: domini generati algoritmicamente. Molti NXDOMAIN, sottodomini ad alta entropia, stesso TLD.
Quando cerchi malware in un PCAP. Il beaconing è il pattern più frequente.

Estrazione file da PCAP

Se il PCAP contiene un malware scaricato, estrailo e analizzalo separatamente. In CTF spesso la flag è dentro un file trasferito via HTTP/SMB.
# Wireshark - GUI
# File -> Export Objects -> HTTP (o SMB, FTP, TFTP)
# Seleziona i file, salvali, analizzali

# NetworkMiner - GUI
# Carica PCAP, estrae automaticamente file, credenziali, host, sessioni

# Zeek - CLI, log strutturati
zeek -r traffico.pcap
ls *.log  # conn.log, dns.log, http.log, ssl.log, files.log, weird.log
Dopo aver identificato traffico HTTP/SMB nel PCAP. Sempre, per recuperare file trasferiti.

Zeek - dal PCAP ai log

Zeek trasforma un PCAP in log strutturati (TSV) interrogabili con grep/awk. Se il PCAP è grande (GB), Wireshark è lento: Zeek produce log in minuti e li navighi da shell.
# Installazione (Ubuntu/Debian)
sudo apt install zeek

# Analisi PCAP: genera log nella cartella corrente
zeek -r traffico.pcap

# Log generati:
# conn.log    - connessioni (IP, porta, durata, byte)
# dns.log     - query DNS
# http.log    - richieste HTTP
# ssl.log     - sessioni TLS
# files.log   - file trasferiti
# weird.log   - anomalie protocollari

# Leggere conn.log con zeek-cut
cat conn.log | zeek-cut id.orig_h id.resp_h id.resp_p proto duration

# Filtrare DNS per query più frequenti
cat dns.log | zeek-cut query | sort | uniq -c | sort -rn | head
Quando il PCAP è grande (oltre 500 MB) o quando vuoi fare analisi statistica su molte connessioni.

tshark - analisi CLI

tshark è la versione CLI di Wireshark. Utile per script, per PCAP grandi, per estrarre campi in CSV e passarli ad awk/grep.
# Statistiche: Protocol Hierarchy
tshark -r traffic.pcap -q -z io,phs

# Statistiche: conversazioni TCP
tshark -r traffic.pcap -q -z conv,tcp

# Filtra e salva un sottoinsieme
tshark -r grande.pcap -Y 'http.request.method == "POST"' -w post_only.pcap

# Estrai campi in CSV
tshark -r traffic.pcap -Y "http.request" -T fields -e ip.src -e http.host -e http.request.uri -E separator=,

# Decodifica porta non standard come HTTP
tshark -r traffic.pcap -d tcp.port==8080,http -Y "http"
Quando devi automatizzare (script) o quando Wireshark è troppo lento per un PCAP grande.

tcpdump - cattura

tcpdump è il tool di cattura su qualsiasi sistema Linux/macOS. Semplice, affidabile, presente di default.
# Cattura su interfaccia eth0 e salva
sudo tcpdump -i eth0 -w cattura.pcap

# Leggi un file già catturato
tcpdump -r cattura.pcap

# Filtro BPF: solo porta 443, max 100 pacchetti
tcpdump -r cattura.pcap -c 100 'tcp port 443'

# Output ASCII: mostra il payload in chiaro
tcpdump -r cattura.pcap -A 'host 10.0.0.5 and port 80'
Quando devi catturare traffico live in un lab, o quando non hai Wireshark a disposizione.

Checklist Network Forensics

Un ordine chiaro ti fa risparmiare minuti. Non saltare passaggi: ogni step restringe il campo per il successivo.
  1. Overview: Protocol Hierarchy, Conversations, Endpoints
  2. Identifica host sospetti (volumi anomali, connessioni a IP strani)
  3. Analizza DNS: query sospette, DGA, tunneling, NXDOMAIN
  4. Analizza HTTP: User-Agent, POST, download, Basic Auth
  5. Analizza TLS: SNI, certificati, cipher suite
  6. Estrai file con Export Objects / NetworkMiner
  7. Genera log Zeek per analisi strutturata su PCAP grandi
  8. Correla con timeline (quando è successo cosa)
Sempre, quando analizzi un PCAP da zero. Segui l'ordine.

3.2 Log Analysis & Incident Response

I log dicono cosa è accaduto dentro la macchina. Complementari al PCAP: uno dice cosa è transitato in rete, l'altro cosa è successo dentro l'host.
In CTF, i log sono spesso la fonte primaria (più facili da leggere del PCAP). Un .evtx di Windows contiene centinaia di eventi: sapere quali Event ID cercare è la differenza tra 5 minuti e 2 ore.

Windows Event Log - Canali

Windows organizza i log in "canali". Ogni canale ha uno scopo. Sapere dove guardare è il primo passo.
  • Security: autenticazioni, accessi, permessi. Il canale più importante.
  • System: avvii, servizi, driver. Utile per persistence (servizi installati).
  • Application: applicazioni. Raramente utile in CTF.
  • Microsoft-Windows-Sysmon/Operational: se Sysmon installato. Il canale più ricco per detection.
  • Microsoft-Windows-PowerShell/Operational: esecuzione PowerShell. Fondamentale per PowerShell offuscato.
  • Microsoft-Windows-TaskScheduler/Operational: scheduled tasks. Persistence classica.

File in C:\Windows\System32\winevt\Logs\ con estensione .evtx. Sono binari, non testuali: servono tool dedicati (EvtxECmd, Event Viewer, Chainsaw).

Quando hai file .evtx da analizzare. Inizia sempre dal canale Security, poi System, poi Sysmon se presente.

Chainsaw / Hayabusa / DeepBlueCLI

Parsare i log è solo il primo passo. Il passo successivo è cercare pattern sospetti automaticamente con regole Sigma. Questi tre tool applicano regole Sigma a file .evtx offline.
# Chainsaw - hunting su .evtx con regole Sigma
chainsaw hunt /path/to/evtx/ --sigma /path/to/sigma/rules/ --mapping /path/to/mappings/sigma-event-logs-all.yml --output results.csv --csv

# Hayabusa - scan completo con timeline
hayabusa.exe csv-timeline -d /path/to/evtx/ -o timeline.csv

# DeepBlueCLI - PowerShell, script leggibile
.\DeepBlue.ps1 -log .\Security.evtx
Dopo aver parsato i .evtx con EvtxECmd. Chainsaw e Hayabusa sono più veloci e completi; DeepBlueCLI è didattico (script leggibile).

Sigma rules

Sigma è un formato standard per scrivere regole di detection indipendenti dal SIEM. Una regola Sigma è un file YAML che descrive cosa cercare. Strumenti come Chainsaw la traducono in query native.
# Esempio: regola per Mimikatz DCSync
title: Mimikatz DC Sync
id: 2030ad8f-0b7d-4e3c-bc40-2b3a45f43e1d
status: stable
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4662
    ObjectType: '%{19195a5b-6da0-11d0-afd3-00c04fd930c9}'
    Properties|contains:
      - '1131f6aa-9c07-11d1-f79f-00c04fc2dcd2'
      - '1131f6ad-9c07-11d1-f79f-00c04fc2dcd2'
  condition: selection
level: high
tags:
  - attack.credential_access
  - attack.t1003.006
Quando devi scrivere una detection rule o capire come funziona una regola esistente. Il repo pubblico SigmaHQ ha migliaia di regole pronte.

Linux logging

Su Linux i log sono file di testo in /var/log. Più semplici da leggere di .evtx (nessun tool dedicato), ma serve sapere dove guardare.
# File di log principali
/var/log/auth.log      # Debian/Ubuntu: autenticazioni, sudo, SSH
/var/log/secure        # RHEL/CentOS: equivalente
/var/log/syslog        # Log generici di sistema
/var/log/kern.log      # Kernel
/var/log/apache2/      # Web server
/var/log/audit/audit.log # Auditd (se installato)

# Cercare login falliti per IP
grep "Failed password" /var/log/auth.log | awk '{print $11}' | sort | uniq -c | sort -rn | head

# Cercare comandi sudo
grep "sudo:" /var/log/auth.log | tail -50

# journalctl (systemd)
journalctl -b                                          # boot corrente
journalctl -p err                                      # solo errori
journalctl -u nginx                                    # solo unit nginx
journalctl --since "2026-04-15 09:00" --until "2026-04-15 17:00"
journalctl -o json -u sshd                             # output JSON

# auditd - audit di sicurezza dettagliato
ausearch -k user_modify                                # eventi con chiave
ausearch --start today -m USER_LOGIN                   # login di oggi
aureport --summary                                     # riepilogo
Quando hai un dump di log Linux. Inizia da auth.log/secure per autenticazioni, poi journalctl per eventi di sistema.

Detection di tecniche comuni

Queste sono le tecniche che in CTF trovi più spesso. Impara a riconoscerle a colpo d'occhio.

Password spraying (T1110.003)

L'attaccante prova UNA password comune (es. "Primavera2026!") contro MOLTI utenti. Evita il lockout perché ogni utente ha pochi tentativi falliti.
  • Cluster di eventi 4625 con TargetUserName diversi
  • Status/SubStatus consistenti (es. 0xC000006A = password errata)
  • Stesso IpAddress o pattern temporale stretto
Quando vedi molti 4625 in poco tempo con utenti diversi dallo stesso IP.

Kerberoasting (T1558.003)

L'attaccante richiede ticket di servizio (TGS) per account con SPN. Il TGS è cifrato con la password dell'account di servizio, crackabile offline. Non serve essere admin: qualsiasi utente di dominio può farlo.
  • Eventi 4769 con TicketEncryptionType = 0x17 (RC4)
  • In ambienti AES-only, RC4 è IoC quasi perfetto
  • Query Splunk: index=windows EventCode=4769 TicketEncryptionType=0x17 | stats count by TargetUserName, ServiceName, src_ip
Quando hai log di Active Directory. Cerca 4769 con encryption type RC4.

Pass-the-Hash / Pass-the-Ticket (T1550)

L'attaccante usa hash NTLM o ticket Kerberos rubati per autenticarsi come un altro utente senza conoscere la password in chiaro.
  • Eventi 4624 con Logon Type 3 da host insoliti
  • AuthenticationPackageName NTLM in ambienti Kerberos-only
  • Orari fuori norma dell'account
Quando vedi 4624 Type 3 insoliti, specialmente con NTLM in ambienti che dovrebbero usare Kerberos.

Lateral movement via PsExec/SMB (T1021.002)

L'attaccante esegue comandi remoti su un altro host via PsExec o tool equivalenti. Lascia una firma riconoscibile: servizio temporaneo con nome casuale.
  • Host sorgente: 4648 (logon explicit credentials)
  • Host destinazione: 7045 (service installed) con ServiceName casuale (8 char alfanumerici)
  • Host destinazione: 4624 Logon Type 3 dal sorgente
  • ImagePath temporaneo: C:\Windows\PSEXESVC.exe o simile
Quando vedi 7045 con nome servizio casuale, seguito da 4624 Type 3 dal sorgente.

PowerShell offuscato (T1059.001)

L'attaccante esegue PowerShell con argomenti in Base64 per oscurare il comportamento. Sembra rumore, in realtà è codice.
  • Eventi 4104 (Script Block Logging) con contenuto che include -enc, -encodedCommand
  • Blob Base64 lunghi nel command line
  • Sysmon event 1 con CommandLine sospetto
Quando vedi 4104 o Sysmon 1 con argomenti encoded.

Log clearing (T1070.001)

L'attaccante cancella il Security log per coprire le tracce. Ma il log successivo registra che è stato cancellato.
  • Evento 1102 nel canale Security
  • Allarme critico se non autorizzato
Sempre sospetto. Se vedi 1102, c'è stato un attacco.

Timeline analysis

Un incidente ricostruito senza timeline è un elenco di fatti senza significato. La timeline allinea cronologicamente TUTTI gli eventi da fonti diverse: log Windows, log Linux, traffico rete, metadati file system.
# Plaso / log2timeline: aggrega artefatti in una supertimeline
log2timeline.py --storage-file timeline.plaso /path/to/evidence/

# Esporta in CSV navigabile
psort.py -o l2tcsv -w timeline.csv timeline.plaso

# Filtra per data (utile per isolare una finestra temporale)
psort.py -o l2tcsv -w timeline.csv timeline.plaso "date > '2026-04-15 09:00:00'"

# Navigazione: Timeline Explorer (GUI) o Timesketch (web collaborativo)
# Pivoting temporale: identificato evento sospetto, espandi +/-15 minuti
# Spesso eventi adiacenti rivelano il contesto
Quando hai artefatti da fonti diverse e vuoi ricostruire la storia completa. Sempre nel report finale.

Ciclo IR in pratica

Il NIST SP 800-61 definisce 4 fasi del ciclo IR. In CTF usi solo la fase 2 (Detection & Analysis), ma conoscerle tutte ti serve per capire il contesto.
  1. Preparation: playbook, tool, baseline, esercitazioni. Si fa PRIMA dell'incidente.
  2. Detection & Analysis: validare, classificare, correlare, identificare perimetro. In CTF è tutto qui.
  3. Containment: isolare host, bloccare account, rotare credenziali, bloccare IP C2. In CTF non si fa.
  4. Eradication: reimaging, rimuovere persistenza, patchare vulnerabilità. In CTF non si fa.
  5. Recovery: riportare in produzione, monitoraggio rafforzato. In CTF non si fa.
  6. Post-Incident: lessons learned, aggiornare playbook, detection engineering, IoC sharing. In CTF il writeup è la versione ridotta.
Sempre come cornice mentale. In CTF ti concentri sulla fase 2.

3.3 Memory Forensics

La RAM contiene ciò che il disco non vede: processi, connessioni, credenziali, codice iniettato. Si perde al riavvio.

Perché la RAM è importante

Un malware "fileless" che gira solo in memoria è invisibile all'antivirus classico e alla forensics di disco. In memoria è perfettamente analizzabile. Inoltre, la RAM contiene credenziali in chiaro o in forma facilmente reversibile.
La RAM è la memoria volatile dove il sistema operativo tiene tutto quello che sta facendo in questo momento: processi, aree di codice e dati, connessioni di rete aperte, file mappati, credenziali derivate, segreti delle sessioni TLS attive, comandi appena digitati.
Quando hai un dump di memoria (.raw, .dmp, .vmem, .lime). Sempre prima del disco, perché si perde al riavvio.

Acquisizione

Prima di analizzare, serve catturare. L'acquisizione produce un file dump che contiene una copia byte per byte di tutta la memoria fisica. La dimensione corrisponde alla RAM installata.

Windows

# WinPmem - tool open source, output raw
winpmem.exe -o memory.raw

# DumpIt - single-exe, zero configurazione
DumpIt.exe /O C:\memory.dmp

# Magnet RAM Capture (GUI) - freeware con registrazione
# FTK Imager - supporta anche disk imaging

Linux

# LiME - kernel module, richiede compilazione
sudo insmod lime-*.ko "path=/mnt/ext/memory.lime format=lime"

# AVML - userspace, richiede meno privilegi
sudo ./avml output.lime

VM

# VirtualBox: core dump navigabile
VBoxManage debugvm <nome_vm> dumpvmcore --filename=dump.core

# VMware: snapshot con "Include memory in snapshot" produce .vmem

# QEMU/KVM: dump live
virsh dump <domain> --live dump.file
Quando devi acquisire memoria da un sistema (live o VM). In CTF il dump è già fornito, ma sapere come si acquisisce ti serve per capire i limiti.

Volatility 3 - Sintassi base

Volatility è il framework di riferimento per memory forensics. Volatility 3 (Python 3) è la versione moderna. Rileva automaticamente il profilo dal dump.
# Sintassi generale
vol -f <memory_dump> <platform>.<plugin> [opzioni]

# Info base: versione Windows, build, architettura
vol -f memory.raw windows.info

# Linux
vol -f memory.raw linux.info
Sempre come primo comando su un dump. Ti dice cosa stai analizzando.

Plugin processi

I processi sono il primo oggetto di analisi. Volatility offre plugin diversi che li esaminano da angolazioni diverse: pslist (lista canonica), psscan (pool scan, trova nascosti), pstree (albero), cmdline (argomenti).
# Lista processi (kernel linked list) - il più veloce
vol -f memory.raw windows.pslist

# Pool scan: cerca strutture EPROCESS per tag
# Trova processi nascosti da rootkit o già terminati
vol -f memory.raw windows.psscan

# Albero processi: relazioni parent/child
vol -f memory.raw windows.pstree

# Command line di ogni processo
vol -f memory.raw windows.cmdline

# DLL caricate in un processo specifico
vol -f memory.raw windows.dlllist --pid <PID>
Sempre dopo windows.info. Incrocia pslist + psscan: se un processo compare in psscan ma NON in pslist, è quasi sempre segno di manipolazione della kernel linked list (rootkit).

Plugin rete

Estrae connessioni e socket in ascolto dalla memoria. Un processo "pulito" come PowerShell con una connessione TCP attiva verso un IP esterno è il pattern di un beacon C2.
# Connessioni e socket
vol -f memory.raw windows.netscan

# Output: Offset, Proto, LocalAddr:Port, ForeignAddr:Port, State, PID, Owner
# Cerca: processi non-network (powershell, cmd, rundll32) con connessioni attive
Sempre dopo i processi. Cerca connessioni anomale da processi non-network.

Code injection

Il code injection è la tecnica con cui un attaccante fa girare il proprio codice dentro un processo legittimo. malfind cerca pagine di memoria RWX (Read+Write+eXecute) con MZ header, tipiche di shellcode iniettato.
# Ricerca pagine RWX con MZ header (PE iniettato)
vol -f memory.raw windows.malfind

# Output: Process, Address, Protection, Hex dump
# Se vedi MZ (4D 5A) in una pagina RWX di explorer.exe, è injection

# Per analisi approfondita di singole regioni di memoria
vol -f memory.raw windows.vadinfo --pid <PID>
Sempre. malfind è il plugin più iconico di Volatility.

Credenziali

Windows tiene le credenziali in memoria (LSASS) per Single Sign-On, share, VPN. Sono in chiaro o in forma facilmente reversibile. Volatility le estrae.
# Hash NTLM locali (da LSASS)
vol -f memory.raw windows.hashdump

# Output: utente:RID:LM:NTLM (formato pwdump)
# L'hash NTLM è direttamente sfruttabile in Pass-the-Hash

# Segreti LSA (credenziali cached, chiavi servizi)
vol -f memory.raw windows.lsadump

# Credenziali cached (MSCACHE_V2, crackabili offline)
vol -f memory.raw windows.cachedump
Quando cerchi credenziali. In CTF è un obiettivo frequente.

Registry in memoria

Il registro di Windows è caricato in memoria dal kernel. Volatility permette di ispezionare le hive dal dump senza accedere al disco.
# Elenca hive caricate
vol -f memory.raw windows.registry.hivelist

# Print chiave specifica (es. Run keys per persistence)
vol -f memory.raw windows.registry.printkey --key "Software\Microsoft\Windows\CurrentVersion\Run"

# UserAssist: quali programmi sono stati lanciati dall'interfaccia grafica
vol -f memory.raw windows.registry.userassist
Quando cerchi persistence. Le Run keys sono il posto più comune.

Rootkit detection

I rootkit manipolano strutture kernel per nascondere la propria presenza. Rilevarli richiede confrontare viste multiple dello stesso dato.
# Callback registrate (target di rootkit kernel-mode)
vol -f memory.raw windows.callbacks

# SSDT hook (System Service Descriptor Table)
vol -f memory.raw windows.ssdt

# Driver caricati
vol -f memory.raw windows.driverscan
Sempre, anche se i rootkit kernel-mode sono rari nel 2026. Controllo di routine.

MemProcFS - memory come filesystem

MemProcFS monta il dump come filesystem navigabile. Ogni processo è una cartella, ogni regione di memoria un file. Ottimo per esplorazione iniziale e condivisione con chi non conosce Volatility.
# Windows
MemProcFS.exe -device C:\memory.raw -mount M:

# Linux (richiede FUSE)
./memprocfs -device /tmp/memory.raw -mount /mnt/memory

# Struttura
M:\pid\<PID>\     # processi (command line, modules, threads, handles)
M:\name\<name>\   # raggruppamento per nome processo
M:\sys\            # sistema, registry, drivers
M:\forensic\       # artefatti pre-estratti (YARA scan, pagine sospette)
Quando vuoi esplorare il dump in modo intuitivo, o quando devi condividere con qualcuno che non conosce Volatility.

Workflow Memory Forensics

Un ordine chiaro ti fa risparmiare tempo. Non saltare passaggi: ogni step orienta il successivo.
  1. Acquisizione + hash SHA-256 per integrità (chain of custody)
  2. vol -f memory.raw windows.info - conferma versione Windows
  3. Processi: pslist, psscan, pstree, cmdline. Incrocia i risultati.
  4. Rete: netscan. Cerca connessioni anomale da processi non-network.
  5. Code injection: malfind. Cerca pagine RWX con MZ header.
  6. Persistence: registry.hivelist, printkey Run. Voci sospette in Run key.
  7. Rootkit: callbacks, ssdt, driverscan. Sempre da controllare.
  8. Dump processi sospetti: memmap --dump. Per analisi separata.
  9. Estrazione credenziali (se autorizzato): hashdump, lsadump.
  10. Correlazione con log e PCAP per timeline completa.
Sempre, quando analizzi un dump di memoria. Segui l'ordine.

3.4 Disk Forensics & File Carving

Il disco conserva memoria lunga: file, artefatti, attività utente, file cancellati recuperabili. È la fonte che risponde a "cosa è successo prima".

Perché il disco è importante

La RAM si perde allo spegnimento, il PCAP va catturato in tempo reale, ma il disco conserva tracce per mesi o anni. File cancellati sono spesso recuperabili. Artefatti Windows accumulano tracce di attività utente anche vecchie.
Il disco conserva: file creati anni fa, file cancellati recuperabili, artefatti Windows (Prefetch, ShimCache, AmCache, ShellBags, JumpList, LNK, SRUM), browser history, registry hive, Volume Shadow Copies.
Quando hai un disk image (.dd, .E01, .vmdk) o quando la RAM non è disponibile.

NTFS essentials

NTFS è il file system di Windows dal 1993. Introduce caratteristiche forensi ricche: $MFT strutturata, journaling multi-livello, alternate data streams.

$MFT (Master File Table)

Ogni file e cartella su NTFS ha una entry in un file speciale chiamato $MFT. Una entry di 1024 byte contiene tutte le informazioni sul file.
  • $STANDARD_INFORMATION: timestamp MACB (Modified, Accessed, Changed, Born)
  • $FILE_NAME: altro set timestamp, nome file
  • $DATA: dati residenti o non residenti
Sempre quando analizzi un disco Windows. MFTECmd lo parsifica in secondi.

$LogFile e $UsnJrnl:$J

$LogFile è il journal transazionale NTFS. $UsnJrnl:$J è un journal più accessibile che registra cambiamenti ai file. Se un attaccante cancella file, il journal conserva il record.
# Parsing del journal
MFTECmd.exe -f C:\Evidence\$J --csv C:\Output\ --csvf usn.csv
Quando cerchi file cancellati o modifiche recenti.

Alternate Data Streams (ADS)

NTFS supporta stream multipli per file. Un attaccante può nascondere un eseguibile dentro un file apparentemente innocuo: notepad.exe:malware.exe. Invisible a Explorer ma eseguibile.
# Rilevamento ADS in PowerShell
Get-Item C:\cartella\file.txt -Stream *

# Zone.Identifier: annota URL di origine file scaricati
Quando cerchi payload nascosti o file scaricati da Internet.

Artefatti di esecuzione

Windows tiene traccia dei programmi eseguiti in diversi artefatti. L'incrocio permette di ricostruire cosa è stato lanciato anche senza log specifici.

Prefetch

Windows pre-carica in memoria le risorse delle applicazioni lanciate di frequente. Come effetto collaterale, produce file .pf che registrano nome binario, run count, ultime 8 esecuzioni, file/DLL usati.
PECmd.exe -d C:\Windows\Prefetch\ --csv C:\Output\ --csvf prefetch.csv
Quando cerchi esecuzioni di programmi. Un file Prefetch con run count = 1 per un binario "di sistema" è sospetto.

ShimCache / AppCompatCache

ShimCache è un meccanismo Windows per tracciare le applicazioni ai fini di compatibilità. Come effetto collaterale, registra path binario, timestamp ultima modifica, flag esecuzione. Persistente, sopravvive a cancellazione binario.
AppCompatCacheParser.exe -f C:\Evidence\SYSTEM --csv C:\Output\ --csvf shimcache.csv
Quando cerchi esecuzioni storiche (mesi fa). Attenzione: la semantica varia tra versioni di Windows.

AmCache

AmCache è l'evoluzione più recente. Registra path binario, hash SHA-1, prima esecuzione, publisher, versione. L'hash SHA-1 permette di identificare univocamente i binari eseguiti.
AmcacheParser.exe -f C:\Windows\AppCompat\Programs\Amcache.hve --csv C:\Output\ --csvf amcache.csv
Quando cerchi hash di binari eseguiti. Confronta con VirusTotal/MalwareBazaar.

Correlazione dei tre

Prefetch + ShimCache + AmCache = quadro completo dell'attività. Un binario in tutti e tre è esecuzione documentata a 3 fonti indipendenti. Un binario in uno solo merita indagine.
Parsifica tutti e tre, poi incrocia i risultati per path o hash.
Sempre, in un'analisi di disk forensics seria.

Artefatti di attività utente

Windows registra cosa l'utente ha fatto: cartelle visitate, file aperti, USB collegati. Questi artefatti rispondono a "chi ha fatto cosa".

ShellBags

Entry di registro che Windows scrive quando un utente naviga cartelle tramite Explorer. Persistono anche dopo che la cartella è stata cancellata o l'USB scollegato.
SBECmd.exe -d C:\Evidence\UserProfiles\ --csv C:\Output\ --csvf shellbags.csv
Quando cerchi cartelle visitate. Una ShellBag per F:\Documents\Riservati\ rivela che l'utente ha visitato quella cartella, anche se il drive F: non è mai più stato collegato.

JumpList

Le JumpList sono le liste di file e cartelle recentemente usate mostrate da Windows cliccando con il tasto destro su un'icona della Taskbar.
JLECmd.exe -d C:\Users\user\AppData\Roaming\Microsoft\Windows\Recent\ --csv C:\Output\ --csvf jumplists.csv
Quando cerchi file aperti per applicazione.

LNK files

I file .lnk (shortcut) contengono metadati ricchi: path target, dimensione, timestamp, hostname, MAC address, volume serial number del volume che ospitava il file target.
LECmd.exe -d C:\Users\user\AppData\Roaming\Microsoft\Windows\Recent\ --csv C:\Output\ --csvf lnk.csv
Quando cerchi file aperti di recente. Un LNK in Recent di un file su USB rivela il serial number del volume USB collegato.

Recycle Bin

Il cestino di Windows conserva file cancellati. Ogni file produce due file: $I (metadata) e $R (contenuto).
RBCmd.exe -d C:\$Recycle.Bin\ --csv C:\Output\ --csvf recyclebin.csv
Quando cerchi file cancellati. Utile perché in molti incidenti i file malevoli vengono spostati lì dall'antivirus.

SRUM e Windows Timeline

SRUM

SRUM è un database che traccia l'uso di risorse per applicazione. Registra bytes inviati/ricevuti via rete, CPU time, disco, power. Il valore forense: anche per un malware di cui non c'è altro log, SRUM registra i byte inviati/ricevuti via rete.
SrumECmd.exe -f C:\Windows\System32\sru\SRUDB.dat -r C:\Evidence\SOFTWARE --csv C:\Output\
Quando cerchi esfiltrazione retroattiva. Anche mesi dopo.

Windows Timeline

Windows Timeline registra tutte le attività dell'utente (app aperte, file creati/modificati, pagine web visitate) in un database SQLite.
WxTCmd.exe -f C:\Users\user\AppData\Local\...\ActivitiesCache.db --csv C:\Output\
Quando cerchi attività utente storica.

KAPE - triage tool

KAPE (Kroll Artifact Parser and Extractor) automatizza la raccolta di tutti gli artefatti forensi standard da un host. Poi passa il tutto a tool di parsing (inclusa la suite Zimmerman).
# Raccolta artefatti base
kape.exe --tsource C: --target !BasicCollection --tdest C:\Triage\

# Raccolta + parsing immediato (produce CSV navigabili)
kape.exe --tsource C: --target !BasicCollection --tdest C:\Triage\ --mdest C:\Parsed\ --module !EZParser
Sempre come primo passo in un'analisi di disk forensics. Risparmia ore di parsing manuale.

Browser forensics

Il browser è una delle applicazioni più usate. Lascia artefatti preziosi: cronologia, cookie, credenziali salvate, form data.

Chrome / Edge (Chromium)

  • C:\Users\<user>\AppData\Local\Google\Chrome\User Data\Default\
  • History: cronologia, download, chiavi ricerca (SQLite)
  • Cookies: cookie sessione (SQLite)
  • Login Data: credenziali salvate (cifrate con DPAPI)
  • Web Data: form data, metodi pagamento
  • Bookmarks: JSON

Firefox

  • C:\Users\<user>\AppData\Roaming\Mozilla\Firefox\Profiles\<profile>\
  • places.sqlite: history, bookmark
  • cookies.sqlite: cookie
  • logins.json + key4.db: credenziali

Strumenti

  • DB Browser for SQLite: GUI gratuita per SQLite
  • Hindsight: parsing automatico Chromium, export CSV/JSON/XLSX
  • Autopsy: moduli browser analysis aggregati
Quando cerchi cronologia navigazione, cookie rubati, credenziali salvate.

Autopsy e The Sleuth Kit

TSK è la libreria CLI di riferimento per analisi di file system. Autopsy è la GUI costruita sopra. Supportano NTFS, FAT, ext2/3/4, HFS+, UFS, YAFFS2.

TSK (CLI)

# Layout partizioni di un disk image
mmls evidence.dd

# Elenca file (anche cancellati) su una partizione
fls -r -o 2048 evidence.dd

# Estrai contenuto di un file via inode
icat -o 2048 evidence.dd 42315 > recovered_file.pdf

# Info generali sul file system
fsstat -o 2048 evidence.dd

# Dettagli di un inode specifico
istat -o 2048 evidence.dd 42315

Autopsy (GUI)

  • Carica disk image (E01, raw, VMDK, VHD)
  • Navigazione file system con visualizzazione file cancellati
  • Ricerca keyword con indicizzazione full-text
  • Timeline integrata
  • Moduli browser, registry, email, EXIF, YARA
TSK quando devi scriptare o lavorare da shell. Autopsy quando vuoi GUI e analisi prolungata.

File carving

Il file carving recupera file dal contenuto grezzo di un dispositivo, senza affidarsi al file system. Utile per: file cancellati non ancora sovrascritti, dispositivi danneggiati.

Signature comuni

  • JPEG: inizia FF D8 FF, finisce FF D9
  • PNG: inizia 89 50 4E 47, finisce con chunk IEND
  • PDF: inizia %PDF-, finisce %%EOF
  • ZIP: inizia 50 4B 03 04
  • EXE: inizia MZ (4D 5A)

Strumenti

# PhotoRec - tool classico, recupera foto e documenti
sudo photorec

# Foremost - riconosce decine di signature
foremost -t jpg -i evidence.dd -o recovered/

# Scalpel - configurable tramite scalpel.conf
scalpel -c scalpel.conf evidence.dd -o output/

# bulk_extractor - carving non di file ma di feature (email, URL, IP, carte credito)
bulk_extractor -o output/ evidence.dd
Quando devi recuperare file cancellati o da dispositivi danneggiati. In CTF spesso la flag è in un file cancellato.

Plaso / log2timeline

Aggrega tutti gli artefatti in una supertimeline unica. Oltre 100 parser: EVTX, registry, browser history, prefetch, $MFT, cloud logs. Tutto unificato per timestamp.
# Crea supertimeline da disk image
log2timeline.py --storage-file timeline.plaso evidence.dd

# Esporta in CSV navigabile
psort.py -o l2tcsv -w timeline.csv timeline.plaso

# Navigazione con Timeline Explorer o Timesketch (web collaborativo)
Sempre, per un'analisi di disk forensics seria. La supertimeline è lo strumento di correlazione finale.

Volume Shadow Copies, BitLocker

VSS

Windows crea automaticamente snapshot periodici del volume di sistema. Conservano versioni precedenti di file, spesso pre-compromissione. Un attaccante che cancella un file può comunque aver lasciato la versione originale in uno shadow copy.
# Elenca shadow copies
vssadmin list shadows

# Monta come volumi accessibili
# Arsenal Image Mounter (GUI) o Autopsy (moduli per estrazione VSS)
Quando cerchi versioni precedenti di file. Spesso la chiave di un'indagine.

BitLocker

BitLocker è la soluzione di cifratura full-disk integrata in Windows Pro/Enterprise. Quando un disco è cifrato, l'accesso forense richiede una delle chiavi di recovery.
  • Richiede recovery key (48 cifre) o BEK file o TPM
  • dislocker: Linux, free open source
  • Arsenal Image Mounter: commerciale, supporto BitLocker in versione Pro
Quando il disco è cifrato con BitLocker. In CTF raramente, ma possibile.

Altri file system

  • APFS (macOS): TSK supporta nelle versioni recenti. Alternativa: apfs-fuse per Linux.
  • ext4 (Linux): TSK supporta. debugfs per interrogazione diretta.
# ext4 info filesystem
debugfs -R "stats" /dev/sda1

# File cancellati recuperabili
debugfs -R "lsdel" /dev/sda1
Quando il disk image non è Windows. macOS o Linux.

Workflow Disk Forensics

Un ordine chiaro ti fa risparmiare tempo. Il parsing massivo con KAPE è la scorciatoia per non impazzire.
  1. Acquisizione imaging (FTK Imager, dd, dc3dd) + hash SHA-256
  2. mmls evidence.dd - layout partizioni
  3. fsstat -o <offset> evidence.dd - info file system
  4. KAPE per parsing massivo (MFT, Prefetch, AmCache, ShimCache, EventLog, Registry, JumpList, ShellBags, LNK, SRUM)
  5. Plaso per supertimeline
  6. Analisi con Timeline Explorer / Timesketch
  7. Deep dive su artefatti specifici
  8. File recovery (Recycle Bin, fls, carving)
  9. VSS per versioni precedenti
  10. Correlazione con PCAP, log, memory
Sempre, quando analizzi un disk image. Segui l'ordine.

3.5 Malware Analysis

Regola 1: sample live SOLO in VM isolata, senza connessione a Internet reale. Mai su host. Mai con cartelle condivise. Mai con clipboard condivisa.

Perché questa regola è tripla

Un comando sbagliato si corregge al tentativo successivo, ma l'esecuzione di un sample di malware sul sistema host produce conseguenze molto più onerose (reinstallazione OS, perdita dati). Le scuole di volo ripetono tre volte le procedure di emergenza per fissarle in memoria.
Tripla ripetizione della regola + isolamento rete host-only o internal network + nessuna cartella condivisa + nessuna clipboard condivisa + snapshot pulito obbligatorio.
Sempre, quando analizzi un sample. Anche se "sembra innocuo".

Laboratorio

Il setup standard è FlareVM (Windows) + REMnux (Linux) in rete isolata. FlareVM ha tutti gli strumenti di analisi; REMnux emula servizi di rete (INetSim) così il malware crede di parlare con Internet.
  • FlareVM: Windows per analisi malware (Mandiant). Preinstalla centinaia di tool.
  • REMnux: Linux per analisi (Zeltser). Analisi PDF, Office, sandbox network, disassembler.
  • INetSim / FakeNet-NG: emulatori servizi rete. Rispondono a qualsiasi richiesta con risposte fittizie ma plausibili.
  • Rete host-only o internal network, mai bridged/NAT verso Internet
  • Snapshot pulito obbligatorio (rollback dopo ogni sample)
Sempre, prima di analizzare un sample. Il lab va preparato PRIMA, non durante.

Domande a cui rispondere

Un'analisi di malware deve produrre risposte concrete. Queste sei domande sono l'agenda implicita di ogni report.
  1. Cosa fa il binario? (file creati, processi avviati, chiavi registro)
  2. Come si propaga e persiste? (Run key, scheduled task, servizio)
  3. Con chi parla? (domini, IP, protocolli C2)
  4. Cosa esfiltra? (documenti, credenziali, screenshot)
  5. Da dove viene? (famiglia, variante, build)
  6. Come si difende dal rilevamento? (anti-debug, anti-VM, packing)
Sempre, durante l'analisi. Ogni risposta è una sezione del report finale.

Output operativi

Un'analisi di malware produce tre output operativi che il difensore può usare.
  • IoC (Indicator of Compromise): hash, IP, domini, mutex, percorsi. Valori specifici utili per rilevare la stessa minaccia.
  • Regole detection: YARA (binari), Sigma (log), Snort/Suricata (rete). Generalizzazioni degli IoC.
  • TTP mappate ad ATT&CK: la sequenza di tecniche usate, in linguaggio MITRE.
Sempre nel report finale. In CTF, mappa sempre le TTP.

Static analysis - leggere senza eseguire

L'analisi statica è sicura per definizione (il binario non viene eseguito). È veloce (minuti) e orienta tutta l'analisi successiva.

Formato PE (Windows)

Il formato PE è la struttura degli eseguibili Windows. Ogni byte ha un significato definito. Sapere cosa guardare ti orienta.
  • Header MZ, header NT, sezioni (.text, .data, .rsrc, .rdata)
  • Entropia: >7.5 = packed/cifrato. Codice normale ha entropia 5.5-6.5.
  • Nomi sezioni: .upx0, .aspack, .themida = packer specifico. Nomi randomici = sospetto.
  • Import minimi: LoadLibrary + GetProcAddress = packer (tutto risolto a runtime)
  • Risorse anomale: exe da 50 KB con risorsa .rsrc da 2 MB = payload secondario nascosto
  • Timestamp compilazione strano (futuro o passato remoto) = manipolato
Sempre come primo passo, prima di qualsiasi esecuzione.

Tool static

Ogni tool ha uno scopo preciso. Usali in sequenza.
  • PEstudio: triage PE con IoC evidenziati. Sempre il primo strumento aperto.
  • Detect It Easy (DIE): identifica packer, compilatore, entropia per sezione.
  • CFF Explorer: editor PE completo.
  • PE-bear: analisi e diffing PE. Utile per confrontare varianti.
  • capa: mappa capability ad ATT&CK automaticamente.
  • FLOSS: estrae stringhe normali + offuscate (stack strings, decoded).
  • YARA: pattern matching contro regole community o proprie.
# Hash del sample (SHA-256 per identificazione univoca)
sha256sum sample.exe

# Detect It Easy: packer, compilatore, entropia
die sample.exe

# PEstudio (GUI): apri sample.exe, evidenzia IoC

# capa: capability mappate ad ATT&CK
capa sample.exe

# FLOSS: stringhe normali + offuscate
floss sample.exe > strings.txt

# YARA: pattern matching contro ruleset community
yara -r signature-base/yara/ sample.exe
Sempre, prima di eseguire il sample. Il triage statico richiede 5 minuti e produce un quadro orientativo.

Dynamic analysis - osservare in azione

L'analisi attiva completa la statica: mostra cosa il binario fa effettivamente, incluse scelte runtime e payload scaricati. Differenza: statica = leggere sceneggiatura, attiva = vedere film proiettato.

Tool

  • Process Monitor (Procmon): filesystem, registry, processi, rete a livello kernel
  • System Informer: vista live processi, thread, handle, moduli (erede di Process Hacker)
  • Autoruns: snapshot persistenza (Run keys, servizi, tasks, WMI)
  • TCPView: connessioni TCP/UDP con processo associato
  • Wireshark: cattura traffico
  • Noriben: wrapper Procmon con report di sintesi automatico
  • Regshot: snapshot registry pre/post, diff

Sequenza

La sequenza è importante: pre-snapshot, esecuzione, post-snapshot. Se salti un passaggio, perdi dati.
  1. Autoruns + Regshot snapshot pre-esecuzione
  2. Procmon armato con filtro, Wireshark in cattura, Process Hacker in vista
  3. Esecuzione sample (doppio click, o runas se serve contesto)
  4. Osservazione 30-60 secondi
  5. Stop tool
  6. Autoruns + Regshot snapshot post
  7. Noriben report di sintesi
Sempre dopo il triage statico. Mai prima.

Reverse engineering

Statica e attiva portano fino a un certo punto. Per capire perché un byte è cifrato in un certo modo, serve scendere nel codice assembly. Questo è RE, la competenza che distingue analista junior da esperto.
  • Ghidra: decompilatore NSA, open source, multi-piattaforma (x86/x64/ARM/MIPS)
  • IDA Free: disassembler x64 classico (versione Pro = standard industriale)
  • radare2 / Cutter: framework CLI + GUI, ottimo per scripting

Il principio: leggi pseudo-C dal decompilatore, riconosci pattern, annota funzioni con nomi parlanti.

Quando statica e attiva non bastano. Quando devi capire la logica interna del binario.

Time Travel Debugging (TTD)

TTD registra l'esecuzione di un processo come un nastro riavvolgibile. Dopo la cattura, l'analista può tornare indietro nel tempo e ricostruire come una pagina RWX è stata allocata, da quale routine è stato copiato lo shellcode. Ideale per process hollowing, unpacking, anti-analisi.
  • File .run di 50-500 MB
  • Comandi: g- (go backward), p- (step backward), !tt (time travel a punto specifico)
  • Il modulo FLARE è la guida definitiva
Quando devi analizzare process hollowing, unpacking, anti-analisi. Quando il debugger classico non basta.

Anti-analisi

Il malware moderno sa che qualcuno proverà ad analizzarlo. Implementa routine per (a) rilevare l'ambiente di analisi, (b) rendere difficile il RE statico, (c) ostacolare il debug attivo. Riconoscerle è parte del mestiere: non riconoscerle porta a falsi negativi.

Anti-debug

  • IsDebuggerPresent(): API Windows, check primitivo
  • CheckRemoteDebuggerPresent(): variante per debugger remoti
  • Lettura PEB.BeingDebugged (offset 0x02 del PEB)
  • NtQueryInformationProcess(ProcessDebugPort): ritorna handle al debugger
  • Timing con RDTSC: delta abnormi = debug attivo
  • Exception-based: genera eccezione, controlla se handler eseguito

Anti-VM

  • CPUID hypervisor bit (bit 31 di ECX dopo CPUID EAX=1)
  • Stringhe vendor CPU: "VMwareVMware", "VBoxVBox", "Microsoft Hv"
  • Driver VM: VBoxGuest.sys, vmmouse.sys, vmsrvc.sys
  • Processi VM tools: VBoxTray.exe, VMwareTray.exe, vmtoolsd.exe
  • MAC address: 00:05:69 (VMware), 08:00:27 (VirtualBox), 00:15:5D (Hyper-V)
  • Chiavi registro: HKLM\HARDWARE\ACPI\DSDT\VBOX__

Anti-analisi ambientale

  • Numero di file recenti in Recent (utente normale ne ha molti, VM fresca quasi nessuno)
  • Uptime sistema (VM tipicamente minuti, utente reale ore/giorni)
  • Cronologia browser, dimensione Desktop, presenza di file .docx
  • Movimento mouse o digitazione recenti

Packing

  • UPX: open source, unpack con upx -d
  • ASPack, ASProtect: commerciali, anti-debug integrato
  • Themida, VMProtect: professionali, virtualizzazione del codice. Molto difficili da unpackare.
  • MPRESS, PECompact: compressori più leggeri
  • Custom: entropia >7, IAT minimal, stringhe assenti

Offuscamento stringhe

  • Stack strings: stringa costruita istruzione per istruzione. FLOSS le estrae automaticamente.
  • XOR/RC4 con chiave hardcoded: stringa cifrata presente, decifrata on-demand. FLOSS tenta decryption.
  • Stringhe in risorse: payload cifrato nella sezione .rsrc.
  • Stringhe fetched da remoto: non nel binario, scaricate dal C2 dopo connessione. Appaiono solo in analisi attiva.
Sempre durante l'analisi. Se il sample "non fa nulla", probabilmente ha rilevato l'ambiente.

Wireshark / tshark

Wireshark è il tool GUI di riferimento per analisi PCAP. tshark è la versione CLI per script e PCAP grandi.
# Filtri display essenziali (applicabili nella barra in alto di Wireshark)
ip.addr == 10.0.0.5                          # traffico da/verso IP
ip.src == 192.168.1.10 && tcp.port == 443    # IP sorgente E porta
http                                          # solo HTTP
http.request.method == "POST"                 # solo POST
dns                                           # solo DNS
dns.qry.name contains "evil"                  # query DNS contenenti "evil"
tls.handshake.type == 1                       # ClientHello TLS
tcp.flags.syn == 1 && tcp.flags.ack == 0      # solo SYN (nuove connessioni)
kerberos.msg_type == 10                       # AS-REQ
smb2                                          # solo SMB2
ntlmssp                                       # solo NTLM auth

# tshark - statistiche
tshark -r traffic.pcap -q -z io,phs           # Protocol Hierarchy
tshark -r traffic.pcap -q -z conv,tcp         # conversazioni TCP

# tshark - estrarre campi CSV (per pipeline)
tshark -r traffic.pcap -Y "http.request" -T fields -e ip.src -e http.host -e http.request.uri -E separator=,

# tshark - decodificare porta non standard come HTTP
tshark -r traffic.pcap -d tcp.port==8080,http -Y "http"

# tcpdump - cattura live
sudo tcpdump -i eth0 -w cattura.pcap          # cattura su eth0
tcpdump -r cattura.pcap -c 100 'tcp port 443' # leggi, max 100, porta 443
tcpdump -r cattura.pcap -A 'host 10.0.0.5 and port 80'  # payload ASCII

Windows Event Log - Query rapide

PowerShell ha cmdlet native per interrogare eventi. Utile quando hai accesso a un sistema live.

# Filtrare per Event ID
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4625} -MaxEvents 50

# Eventi in un range temporale
Get-WinEvent -FilterHashtable @{LogName='Security'; StartTime=(Get-Date).AddHours(-24)} -MaxEvents 100

# Logon falliti per utente (raggruppati)
Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4625} | Group-Object {$_.Properties[5].Value} | Sort-Object Count -Descending

Get-WinEvent -FilterHashtable @{LogName='Security'; ID=4688} -MaxEvents 50

# Sysmon processi
